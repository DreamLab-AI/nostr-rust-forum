# ADR-2037 — Pin an existing section to a zone from zone config

## Context

A section is a kind-40 channel. The relay decides its zone from the D1 `channel_zones` row, written only by `POST /api/admin/channel-zone`; the clients decide it from the signed kind-40 `section` tag. An operator who wants an existing section to become "admin eyes only" has no clean move: re-signing the kind-40 makes a new channel and strands the posts; rebinding the D1 row is invisible to clients, which keep choosing the old zone's key, and the admin "Bind to zone" button would bind it back. A zone (ADR-2016) is already the unit of read gate, write gate, visibility and encryption key, so a hidden, encrypted zone with an admin-only cohort is exactly "admin eyes only"; what was missing is a way to move a channel into one without rewriting stored data.

## Decision

1. **A zone may pin channels.** `[[zones]] channels = [<kind-40 id>, …]` (64-char lowercase hex). It is projected into `ZONE_CONFIG`, which the relay and both clients already read, and omitted from the projection when empty (`skip_serializing_if`), so a config without pins projects byte-for-byte as before (`nostr-bbs-config/tests/zone_projection.rs`, fixtures captured before the change). Validation refuses a malformed id, a channel listed twice, a channel pinned by two zones, and a pinning zone whose id is `<other zone id>-…` (`validate.rs:539`), because client media routing takes the first prefix match.
2. **The relay consults the pin before D1, everywhere.** `ZoneConfig::pinned_zone` (`zone_config.rs:274`) returns `Unpinned`, `Pinned(zone)` or `Conflict`, comparing ids case-insensitively. A malformed pin list fails closed: a zone whose `channels` holds an entry that is not 64 hex digits, or that carries a misspelt pin key (`channel`, `pin`, `pins`, `pinned`, `pinned_channels`, or anything within edit distance 2 of `channels` in any case; unrelated keys such as `channel_order` are ignored), has every pin it declares answer `Conflict`; 64-hex ids under a misspelt key answer `Conflict` too. A `channels` of the wrong type (a string, non-string elements, `null`) breaks only that zone's pins, any 64-hex ids in it answer `Conflict`, and the rest of `ZONE_CONFIG` loads (before, it made the whole config unparseable and every zone dark). Errors are logged once per isolate. A malformed entry cannot be tied to the channel it meant, so that one channel stays in its D1 zone; config validation (`check_zone_pin_keys`, `validate_channel_pins`, and `validate_zone_config_json` for a hand-edited projection) refuses all of these before deploy. `trust::resolve_channel_zone` (`trust.rs:595`) answers a pinned channel without calling the D1 lookup, so a pinned channel resolves while D1 is down; a `Conflict` is a `ZoneLookupError` (reads withheld from everyone, writes refused). `get_channel_zone` and `cached_channel_zone` (`relay_do/nip_handlers.rs:2969`, pin checked ahead of both 60 s memos, from the `ZoneConfig` snapshot the caller already holds) go through it, and every gate resolves through `cached_channel_zone`: the kind-42 write gate and its ciphertext check, the reference-kind gates, REQ, COUNT, live broadcast, push fan-out and kind-40/41 visibility. The two direct SQL readers outside that path apply the pin themselves: `/api/profile-stats` (`profile_stats.rs:366`, D1 asked only about unpinned channels) and the Jev triage candidate query (`triage.rs:207`). A kind-42 into a pinned channel whose `zk` names another zone is refused (`zone_config.rs:443`), so a client that does not know the pin cannot store old-zone ciphertext even when the pinned zone is unencrypted; the same refusal applies to comments and other reference kinds on messages in a pinned channel.
3. **Clients route a pinned channel by its pinned zone.** `ChannelMeta.section_tag` holds the raw signed tag; `ChannelMeta.section` is `zones::effective_section` (`client-core/src/stores/zones.rs:347`): the pinning zone's id, used verbatim so it resolves by exact match, unless the tag already names that zone. It is set at both kind-40 ingest sites and recomputed on every cache load (`heal_cached_sections`, `channels.rs:73`), and the cache stores the raw tag in `section`, so caches from before the field, a removed pin and an older build all route correctly. Every resolver (key choice, navigation, media target, search, BBS) reads `ChannelMeta::section` and follows with no change of its own. The admin rename modal still mirrors the raw tag onto kind-41.
4. **A pinned channel is never bound in D1.** `POST /api/admin/channel-zone` answers 409 for a channel any pin (or pin misconfiguration) names, and "Bind to zone" and bind-on-create decide through `zones::bind_zone_for`, which returns nothing for a pinned channel; the admin page shows the pin instead. A row written while pinned would decide the zone after the pin is removed.
5. **Channel metadata and edits follow the channel's zone.** A non-admin's kind-41 (rename, description, picture, pin/unpin control) must name a stored kind-40 by its exact id (closing the mixed-case alias that would miss the channel's zone) and needs write access to the channel's resolved zone, as a kind-42 does, after the existing trust-level rule; a channel with no zone stays gated by trust level alone. A kind-42 edit (`["e", <target>, "", "edit"]`) is refused unless its target is a stored message of the same channel (root values compared case-insensitively; a D1 failure gives a retryable "error: … try again"). The reply-topic and edit-target checks run after the zone write gate, so a non-writer learns nothing about which messages exist, and clients apply an edit to a post only when both are filed in the same channel, so an author who lost write access to a pinned channel cannot rewrite its posts from another one.
6. **Clients follow the relay's empty-cohort rule.** `Zone::is_member` (`zones.rs:173`) now treats empty `required_cohorts` as open only on a `Public` zone, so an admin-only zone with no cohort no longer shows as an open tile. Every caller already ORs with `Public` visibility or admin, or pre-filters non-empty cohorts; no zone with cohorts, and no public zone, changes.
7. **Sealed search keeps pinned channels out of other zones' new rows.** `nostr-bbs-search-build --zone-config <file>` (and `NBSS_ZONE_CONFIG` for `scripts/sealed-search-nightly.sh`) skips posts whose channel is pinned to another zone, and excludes those already indexed that the relay still serves the indexer.

No new cryptography, no change to stored event formats, no D1 schema or data change, no new endpoint. Pinning to a `hidden` zone is the intended use; `locked` is allowed and exposes more (below).

## Consequences

**What a pin protects.** Relay reads of the channel's posts, live delivery and push of them, its posts' existence in counts and profile stats, and decryption of everything posted after the move, because clients encrypt new posts to the pinned zone's key, which members of the old zone never receive. With a `hidden` pinned zone the channel's definition and metadata are withheld too.

**`hidden` against `locked`, for a non-member of the pinned zone** (old-zone members and signed-out readers alike):

| Exposed | `hidden` | `locked` |
|---|---|---|
| kind-40 definition: name, description, picture URL, creator pubkey, raw `section` tag | no | yes |
| kind-41 metadata, including the rename history | no | yes |
| kind-42 posts, counts, live delivery, push for posts | no | no |
| reactions, comments, reports on its posts | no | no |
| the zone tile | no | yes, as a locked tile (the new client files the channel there, never under the old zone's tile) |
| NIP-11 `zone_groups` entry (when the zone sets `group_pubkey`) | no | yes |
| Web Push alert for a new kind-40 in the zone | no | yes, for channels created in the zone later; pinning an existing channel stores no new kind-40, so it raises no alert |
| the pinned id and the zone's existence in `ZONE_CONFIG` | yes (page source) | yes (page source) |

**What it does not protect.**
- History already synced or decryptable under the old zone's key stays so: members who fetched the channel's posts before the move keep their copies and the key that opens them, and the posts remain stored under the old zone's key (an export of D1 or a forwarded copy is readable by any holder of that key). Re-sealing history would rewrite data and still miss synced copies; it is not done.
- The zone config, including the pinned channel id and the new zone's existence, is public: it ships in the page source.
- Images already uploaded stay under the old zone's media path and readable to its members; only new uploads go to the pinned zone.
- Kind-42 posts e-tagged by a slug rather than the channel id (pre-id legacy) were never zone-gated by the relay, pin or not: they are delivered unscoped.
- Sealed search: index objects hold event ids and embedding codes (no text), sealed to the old zone's epoch key, so holders of that key can still decrypt the ids and embeddings of the channel's pre-pin posts. An `update` excludes them only when it re-reads them (a reconcile, `--since 0`) and the relay still serves them to the indexer (the indexer is an admin or holds the pinned zone's cohort); exclusion hides rows at search time, and `compact --all` drops them from the objects. A full rebuild leaves them out unless the indexer is served them and runs without `--zone-config`.
- The offline tools `nostr-bbs-zone-migrate` and `nostr-bbs-bulk-import` are not pin-aware: they read `channel_zones` and would seal a pinned channel's history under its old zone, which the relay then refuses (`zk` mismatch).
- Agent accounts (`agent` cohort) are granted a zone's key only when the zone sets `agent_keys = true` (`client-core/src/zone_crypto/mod.rs:71`), so an agent given the pinned zone's cohort reads it through the relay but cannot decrypt new posts unless the pinned zone opts in.

**Behaviour with old builds.** An old relay ignores `channels`: the pin silently does nothing, so the deployed relay must be checked to be at or after this change before a pin is relied on. An old client against a new relay, for a member of the old zone:
- `hidden`: the relay sends nothing for the channel (definition, posts, counts); the client drops its cached channel on the next authenticated EOSE; every post is refused (no write access to the pinned zone).
- `locked`: the relay still sends the definition and metadata, so the old client keeps the section under the old zone's tile (and keeps any stale cached posts), shows no new posts, and has every post refused.

An old admin client still reads, decrypts old posts with the old key and new posts if it holds the pinned zone's key, but every post it writes is encrypted to the old zone and refused (`zk` mismatch), and its "Bind to zone" gets 409. Nothing new leaks; old clients fail closed.

**Rollback (removing a pin).** The channel returns to whatever `channel_zones` says. If it has no row, it becomes unscoped: every post, including those made while pinned, is served to everyone, members and signed-out readers alike, so the rollback runbook must confirm the row exists (and names the intended zone) before the pin is removed. With a row for the old zone, posts made while pinned are served to old-zone members as ciphertext they cannot decrypt (missing-key placeholders), but reactions, report text and any metadata edits made while pinned are plaintext and become visible to them.

**Behaviour changes for channels that are not pinned.** A non-admin's kind-41 into a channel bound to a zone now needs write access to that zone: a TL3 member, or a channel's TL2 creator, who cannot write the zone can no longer rename it, change its picture or post pin control events. A kind-42 edit whose target is not a stored message of the same channel (or whose target lookup fails) is refused, and clients ignore an edit filed in another channel than its target. Neither affects a channel with no zone, admins, or edits any client in this kit publishes.

**Costs.** Several channels pinned to one zone share one section card on the forum index (they all route by the zone id), and a pinned channel's canonical URL moves to the pinned zone's slug (old bookmarks under the old zone's path stop resolving; `/go/<event id>` still works). A pinned channel's zone cannot be shown nested inside its old zone's tile. A channel lookup scans the zones' pin lists in the caller's `ZONE_CONFIG` snapshot; no extra parse, JS call or D1 read per event (ADR-2018), and only a D1 miss re-reads the config. An edit costs one stored-target lookup at write time. The client derives `section` at ingest and on cache load only; a pin change takes effect on the next page load.
